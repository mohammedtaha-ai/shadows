- Transport: the installed native `codex.exe`, launched with
  `app-server --listen stdio:// -c features.multi_agent=false`.
- Protocol: generated by this installed CLI using
  `codex app-server generate-json-schema --out <temporary schema directory>`.
- Handshake: `initialize`, then `initialized`, with client name
  `shadows_codex_probe`, version `0.1.0`, and `experimentalApi: false`.
- Authentication: existing Codex sign-in; `account/read` reported type `chatgpt`.
  No API key was entered, and no auth file or credential was read into the probe
  transcript. Account identity fields were not printed or saved in the result.
- Model: `gpt-6.1-sol`, reasoning effort `low`, service tier `default`.
- Thread: `approvalPolicy: never`, `sandbox: read-only`, `ephemeral: false`.
  The response confirmed sandbox type `readOnly` and `networkAccess: false`.
- Developer instructions limited the model to the requested text and prohibited
  tools, file inspection, agents, and file changes. Unexpected server requests
  would receive an unsupported-method error, not approval.
- Existing Codex configuration was inherited. Hook start/completion events were
  observed. This was not a test of isolated per-thread MCP configuration.

`model/list` returned eight catalog entries and their reasoning effort options.
The default was `gpt-6.1-sol`. Only that model was invoked; catalog presence does
not establish successful inference access to every listed model.

## Real-provider results

Three turns were started: one completed text turn, one interrupted text turn,
and one completed continuation after restarting app-server.

| Check | Observed result |
|---|---|
| Initial handshake | Success, 380 ms |
| Streaming response | Completed, 11 `item/agentMessage/delta` notifications, 9,333 ms from turn request to observed completion |
| Cancellation after streaming began | `turn/interrupt` followed by `turn/completed` with status `interrupted`; 461 ms from interrupt request to observed terminal event |
| First process shutdown | Stdin closed; process exited with code 0; no forced termination |
| Fresh process handshake | Success, 431 ms |
| Resume identity | `thread/resume` returned the same thread ID and two prior turns |
| Resume context | Completed, 11 text delta notifications, exact prior random marker returned without resending it, 14,449 ms |
| Second process shutdown | Stdin closed; process exited with code 0; no forced termination |

Thread ID: `01a1b78c-b16f-7aa1-8de9-c9d44eeec849`.

The first turn asked the model to remember a runtime-random marker and reply
with exactly that marker. It returned `SHADOWS-e6064df76226954b`.
The second requested integers 1 through 10000, one per line. The client waited
for the first text delta, interrupted the turn, and asserted terminal status
`interrupted`, rather than treating an interrupt RPC response as completion.

After closing the first process and launching a fresh one, the third turn asked
for the earlier marker without including its value. It returned exactly
`SHADOWS-e6064df76226954b`. This tests provider-side persisted context, not merely
reloading Shadows' displayed transcript or echoing a marker from a new prompt.

Both completed turns had no turn error. The interrupted turn also reported no
turn error. Notifications included `turn/started`, `item/started`,
`item/completed`, `item/agentMessage/delta`, `thread/tokenUsage/updated`, and
`turn/completed`; the interrupted turn also contained a reasoning item.
No tool or approval round trip was exercised.

## Usage and account limits

The resumed process emitted token usage snapshots. The latest measured snapshot
reported:

| Field | Reported value |
|---|---:|
| `last.inputTokens` | 32,253 |
| `last.cachedInputTokens` | 28,160 |
| `last.outputTokens` | 15 |
| `last.totalTokens` | 32,268 |
| `total.totalTokens` | 55,546 |
| `modelContextWindow` | 665,000 |

These are wire values, not a Shadows context calculation. `total` and `last`
are distinct fields; cumulative usage must not be displayed as current context
occupancy. An initial usage snapshot after resuming and a later update were both
observed. The exact context display mapping still needs a decision and a focused
test before product integration.

`account/rateLimits/read` succeeded and supplied primary and secondary windows
with `usedPercent`, `windowDurationMins`, and `resetsAt`. This establishes that
the protocol supplies account-limit data; it does not measure the cost of this
probe or prove behavior when a limit is exhausted.

## What remains unproven

- Shadows MCP configuration, grant identity, tool execution, and tool results.
- Chat Mode and Agent Mode enforcement, command/file approvals, and refusal UI.
- Model/effort changes during a thread and persistence of those choices.
- Forks, images, attachments, background tasks, and compaction/context re-send.
- Crash recovery, malformed messages, transport failure, and cancellation while
  a command or permission request is active.
- Shadows API/frontend integration, browser acceptance, and product gates.

This baseline supports continuing the direct app-server integration design. It
does not make the disabled Codex entry runnable in Shadows.

## Reference

The official [Codex App Server documentation](https://learn.chatgpt.com/docs/app-server)
describes stdio JSONL, initialization, thread/turn lifecycle, interruption,
resumption, usage, and approvals. Payloads for this probe came from the installed
0.166.0 schemas rather than assuming the online schema version matched the CLI.
