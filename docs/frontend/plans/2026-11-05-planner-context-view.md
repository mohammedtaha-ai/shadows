# Planner Context View Plan (Planner context slice 3)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** draft, 2026-11-05. Not reviewed.

**Goal:** In a Planner conversation, Mohammed sees where the conversation is anchored and changes
or clears it, starts a conversation anchored at a part or an outcome, sees on each turn whether
the planning context was heard, opens what it carried, and asks for it to be sent again.

**Architecture:**
- **One backend task (B-59):** each operation's `invocation` gains `planning_context`:
  `"heard"`, `"prepared"` or `null`. `Harness` owns both the invocation row and the context
  record, so it reads them together. The conversation then knows every turn's state from the
  operations list it already loads, with no request per turn.
- **The web half** uses the routes slices 1 and 2 shipped: `GET/PUT /api/threads/{id}/anchor`,
  `GET /api/operations/{id}/context`, `POST /api/threads/{id}/context/resend`.
- The anchor chip lives in the conversation header beside the stage chip. The record opens in the
  conversation's side panel, where the plan panel opens today.
- A part or outcome page links to the draft with `?anchor=part:<id>` or `?anchor=outcome:<id>`.
  The draft's first send sets the anchor after the thread exists and before the first turn starts,
  so the first turn carries it.

**Spec:** `docs/backend/specs/2026-11-04-planner-context-design.md` §4.1, §4.3 ("On request"),
§4.4, §6 item 3.
**Shared requests:** `docs/shared/requests/2026-11-04-planning-context-routes.md` and
`docs/shared/requests/2026-11-04-planning-context-resend.md` (both accepted);
`docs/shared/requests/2026-11-05-turn-context-state.md` (B-59, asked).

## Global Constraints

- One job per file; no `helpers`/`utils`. Each changed module updates its `contract.yaml`, and
  each new file gets its row in `docs/frontend/codebase/README.md`, in the same commit.
- Types come from `web/src/api/schema.d.ts`, generated by `npm run gen:api`; never hand-edited.
- Every mutation sends a `command_id` kept in an `Attempt` (`web/src/api/command-id.ts`) until it
  succeeds or its content changes.
- Nothing here shows for an AYLUL conversation (`harness === 'aylul'`), as the stage chip does
  today.
- `design` may not import `conversation` (the architecture table): the part and outcome pages
  reach the draft by a router link only.
- Rust lines ≤ 100 characters. `api/openapi.json` changes only with B-59.
- Builders run only their own tests (`npx vitest run <file>`, `cargo test -p <crate> --test
  <name>`); CI runs the full gate.

## Review Focus

1. **The anchored part is removed.** The chip says "Anchored part was removed" and offers Clear;
   it does not fail or show a raw id only. (F-87: `shows_a_removed_anchor`.)
2. **A turn from before slice 1, or a command sent alone** (`/compact`). It has no record: the
   turn shows nothing, and opening is not offered. (F-89: `a_turn_without_a_record_shows_nothing`.)
3. **The draft's anchor call fails after the thread exists.** The person lands in the thread with
   the error and the text, as a failed first turn does today. The retry anchors first, with the
   same command id, and never starts the turn unanchored unless the person chooses to.
   (F-88: `a_retry_sets_the_anchor_first_with_the_same_command_id`.)
4. **Send again while a turn runs, or with no anchor.** The button answers at once ("Your next
   message carries it again"); the running turn is unchanged.
   (F-87: `send_again_says_the_next_message_carries_it`.)
5. **A long record** (over 8 000 tokens, with cuts). The panel scrolls; cuts and the over-budget
   figure are listed above the text, not lost below it. (F-89: `lists_cuts_before_the_text`.)

  parent starts from that parent's first page. `useDesignPages` keeps the loaded pages in local
  state and compares only the revision, which two parents can share.

### Task F-88: Start a conversation anchored at a part or an outcome

**Files:**
- Modify: `web/src/router.tsx` (the draft route's `validateSearch` gains `anchor`),
  `web/src/app/conversation/draft.tsx`, `first-send.ts`, `draft.test.tsx`, `contract.yaml`
- Modify the retry path in the thread: `web/src/app/conversation/carried-send.ts`,
  `use-send.ts`, `composer.tsx`
- Modify: `web/src/app/design/parts-view.tsx`, `roadmap-view.tsx`, `contract.yaml`

**Interfaces:**
- Search value `anchor`: `part:<id>` or `outcome:<id>`; anything else is ignored.
- `useFirstSend(projectId, harness, planId?, profile?, anchor?)`: after `createThread` and before
  `startTurn`, it calls `setAnchor` with its own `Attempt`.
- **A failed anchor never lets the first turn start unanchored by accident:**
  - `CarriedSend` gains `anchor?: { value: ThreadPlanningAnchor; attempt: Attempt }`. When the
    anchor call fails, the thread receives the text, the error and the pending anchor, with its
    `Attempt`.
  - In the thread, `use-send.ts`'s send first calls `setAnchor` with that same `Attempt`, and calls
    `startTurn` only once it succeeds. A lost answer is replayed under the same command id.
  - Beside the error, the composer offers "Send without the anchor". It must not start a turn
    while an anchor write may still land. The server runs a command in a task that outlives the
    connection (`Transport::detached`), so a clear sent alone could commit first, and the first
    write would then set the anchor again. So:
    1. **The first call's outcome is unknown** (no HTTP answer: a network error or a lost
       answer): replay `setAnchor` with the pending `Attempt`, the same `command_id`. Once it
       answers, the first write has settled.
    2. **The first call answered with a refusal** (an HTTP error answer): nothing was saved, so
       skip the replay.
    3. Then send `setAnchor(null)` under its own `Attempt`. Only once the clear succeeds does it
       drop the pending anchor and call `startTurn`.
    4. Any failure on the way keeps the error, keeps whatever is still pending, and starts no
       turn.
  - The pending anchor is dropped once the anchor succeeds.
- The draft shows "Anchored at <name>" above the composer.
- The selected part's page and the selected outcome's page show a link "Plan from here" to
  `/projects/$projectId/new?anchor=…`.

- [ ] Tests (in `draft.test.tsx`):
  - `the_first_send_sets_the_anchor_before_the_turn`: the fake daemon records `PUT …/anchor`
    before `POST …/turns`;
  - `a_failed_anchor_keeps_the_thread_and_the_text`: no `POST …/turns` was made;
  - `a_retry_sets_the_anchor_first_with_the_same_command_id`: the first `PUT …/anchor` loses its
    answer. The retry in the thread sends `PUT …/anchor` with the same `command_id`, then
    `POST …/turns`. One thread exists;
  - `send_without_the_anchor_settles_then_clears`: the first `PUT …/anchor` fails with no answer.
    "Send without the anchor" sends, in this order:
    1. `PUT …/anchor` with the first `command_id`;
    2. `PUT …/anchor` with `anchor: null` and a new `command_id`;
    3. `POST …/turns`.

    The daemon holds no anchor when the turn starts.
  - `send_without_the_anchor_after_a_refusal_only_clears`: the first `PUT` answers 404. No
    replay; `PUT` null, then `POST …/turns`;
  - `an_unknown_anchor_value_is_ignored`.
- [ ] Run `npx vitest run src/app/conversation/draft.test.tsx`; FAIL, implement, PASS.

### Task F-89: Each turn's planning context, and its record

**Files:**
- Create: `web/src/app/conversation/context-mark.tsx`, `context-record-panel.tsx`,
  `context-record-panel.test.tsx`
- Modify: `web/src/app/conversation/messages.tsx` (under the turn's user message),
  `conversation.tsx` (the side panel), `deleted-conversation.tsx`, `contract.yaml`

**Interfaces:**
- Consumes: B-59 (`operation.invocation.planning_context`), F-86 (`carriedContextQuery`).
- `ContextMark` shows under a turn's user message:
  - `"heard"`: "Planning context · heard";
  - `"prepared"`: "Planning context · not confirmed yet" (the turn is still running, or it
    ended without completing);
  - `null`: nothing.
  - Clicking opens the panel.
- **One source for the state.** The mark and the panel both read heard or not from
  `operation.invocation.planning_context` in the operations list. The stream already refreshes
  that list on every operation event (`web/src/stream/refresh.ts`). The record query
  (`carriedContextQuery`) supplies only the text, sources, sizes and cuts, which do not change,
  and its own `heard` field is not shown. A panel opened during a turn therefore turns to "heard"
  when the turn completes, without closing.
- `ContextRecordPanel({ operationId, state, onClose })` shows, in this order:
  - heard or not confirmed yet (from `state`);
  - the sizes: index, detail and over-budget tokens;
  - the cuts, one per line;
  - the sources, one per line: kind, id, version;
  - the text, in a scrolled block.
- **One side panel at a time.** `conversation.tsx` has three today: the plan (`side`), the
  background tasks (`tasksOpen`) and a subagent (`agent`). Each opener closes the other two. The
  context panel joins them as a fourth: opening it closes the other three, and each of the three
  openers, `openAgent` and a live `plan-show` with `place: 'side'` (`showHere`) included, closes
  it.
- The deleted conversation's history (`deleted-conversation.tsx`) also renders `Messages`. It
  shows the mark, read-only: clicking opens the same panel, since a deleted thread's records stay.
  `Messages` gains an `onOpenContext` prop, passed by both screens.
